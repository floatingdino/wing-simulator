# Milestone v0.1: WING-Edit control loop (status after T013 + T015)

Date: 2026-10-25. Branch `task/T013-T015`. T016 owns the full milestone checklist; this file records what T013/T015
delivered and what the first live run showed.

## Run it

```
cargo run --release -p wing-sim -- [--name WINGSIM] [--ip A.B.C.D] [--fw 3.3.4-0-g0c2b9d4a:release] \
    [--model ngc-full] [--scene PATH] [--save-on-exit PATH] [--idle-timeout 10] [--no-meters] [--no-osc]
```

One `ParamStore` is shared by discovery (UDP 2222), the native server (TCP 2222), meter streaming (UDP, sent from
port 2222 like a console) and OSC (UDP 2223). Ctrl-C/SIGTERM stops everything cleanly (about 200 ms). The log shows
connects/disconnects with per-connection counters, one line per burst of sets (count, changed, last path = value),
meter port/report definitions, the ModelRequest answer, and a status line every 60 s.

`--scene` loads a `.snap` with `wing_model::Snapshot::load` (1.x files are migrated) and logs the load report;
`--save-on-exit` writes the store back as `.snap` on shutdown. Checked: `--scene fixtures/PUBLIC.snap` (fw 1.13.9,
snapshot.8) → 21,369 keys, 19,865 applied, 1,755 migrated (8 lossy), 0 unmapped, 0 rejected; save-on-exit wrote a
315 kB `.snap`. The scene file name is offered as the single `$ctl/lib/$scenes` entry.

## Live check with WING-Edit 3.3.4 (passive, no clicks)

- Discovery: WING-Edit probed immediately (from 192.168.20.130:60383) and lists `WING WINGSIM 192.168.20.130
  3.3.4-0-g...`. 180 probe replies in 3 min.
- TCP: **WING-Edit did not connect.** It was showing a modal "Lost connection! Auto reconnect is active." with an OK
  button, left over from an earlier session that ended with a server-side close. Its old socket to :2222 stayed in
  `CLOSED`. In 3.5 min it made no new TCP connection. This matches wing-edit-session.md §3: after a server-side close
  WING-Edit does not reconnect without a user click. Clicking was not allowed (the user's mix is open), so the
  connect/sync/2-minute stay-connected check is **not done**.
- To finish it (human, ~2 min): start `wing-sim`, dismiss the dialog in WING-Edit (OK), select WINGSIM, keep SYNC
  DIRECTION = PC -> MIXER, click CONNECT. Expect log lines: Connected, meter port + reports 0-3, ModelRequest,
  one burst of ~28.7k sets; then it should stay up with report-3 renews every 4 s. Watch the meters for movement.

## Gaps and unverified points

- Not verified with WING-Edit: connect, staying connected, meters animating, edits arriving (the code paths are
  covered by the replay tests).
- ModelRequest reply format (`D7 985729a2 <string>`, no `DE`) is a hypothesis.
- Node definition records: numbered children get an empty name and index; model slots are named after the active
  model; read-only bit = `$` prefix; unit = WING-Edit's unit nibble. Not checked against a real console.
- `$`-list replies: `play/$songs` and `$ctl/lib/$scenes` return their own record with an empty list (configurable via
  `LiveInfo`).
- MIXER -> PC (`DA DC`) reply format is inferred (protocol.md §3.5); WING-Edit never sent it in the captures.
- Meter source/output group sizes come from the schema's io group sizes (local 24, AES50 48, card 64, ...). The
  size WING-Edit expects is unconfirmed.
- Model (`mdl`) changes from one client reach the others as value events for the new defaults; whether a console
  also announces a structure change is open.
- Changes made while a client is mid-push are coalesced per node and sent from that client's thread every <= 10 ms.
